# Короткая записка о решениях

**Capibara · команда PUSH**

Выбрали PostgreSQL 16 и слои raw → core → mart. Исходный raw не меняем; в core сохраняем четыре факта: заказ, позицию, платёж и отзыв, а также шесть измерений. Отказались от модели из агрегатов под известные вопросы: она теряет детализацию. Все пять новых вопросов Q6–Q10 решены без изменения структуры core.

Независимые детали сначала сворачиваем до заказа и только затем соединяем: прямой JOIN завышал выручку на 4,95 %. Ключи и связи защищены PK/FK, деньги — numeric(12,2). Заказы без позиций, платежей или отзывов сохраняем; неизвестные суммы остаются NULL, пустая категория получает `__unknown__`. Противоречия источника отмечаем предупреждениями, не исправляем догадками.

Покупатель определяется по customer_unique_id; адрес хранится в заказе, поэтому переезд не меняет прошлые покупки. Для истории товара добавили product_key и интервалы действия: позиция ссылается на версию на момент заказа. История переживает пересборку core; неизвестное прошлое не восстанавливаем, изменения задним числом, затрагивающие опубликованные продажи, отклоняем.

Выручка — стоимость товаров заказов со статусом `delivered` без доставки; средний чек таких заказов включает доставку. Асимметрия подтверждена контрольными значениями. Правила и допущения документированы; запросы ответов читают только core, mart служит удобным представлением уровня заказа.

Для 550 759 исходных строк выбрали полную сборку core в транзакции. Инкремент и отдельное аналитическое хранилище отложили до измеренной потребности: сейчас они усложняют сопровождение. Проверено: 65 проверок модели — 56 PASS, 9 объяснённых WARN; 56 проверок ответов — PASS. Повторная и чистая сборки совпадают; после добавления историчности все 11 CSV ответов сохранились побайтово.
