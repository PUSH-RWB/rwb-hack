# Бизнес-правила EDA

- Денежные показатели считаются в целых копейках с переводом из Decimal; округление до двух знаков применяется при представлении. Валюта BRL (R$) принята по контексту бразильского датасета; отдельного поля валюты нет.
- «Выручка» в вопросах кейса — сумма price товарных позиций заказов со статусом delivered. Доставка исключена. Это стоимость проданных товаров; комиссия и бухгалтерская выручка площадки не известны.
- Вопрос 1: месяцы оформления с 2016-09-01 включительно до 2018-09-01 исключительно; присутствуют все 24 месяца. Показываются все оформленные заказы и отдельно доставленные; выручка относится к доставленным.
- Вопрос 2: выручка продавца — сумма только его позиций в delivered-заказах. Заказы считаются COUNT DISTINCT order_id; единицы товара — количество строк, поскольку quantity отсутствует и каждая строка соответствует единице. order_item_id — порядковый номер, его нельзя суммировать.
- Вопрос 3: средний чек — сумма price + freight_value по доставленным заказам / число доставленных заказов. Сумма платежей хранится отдельно: она не совпадает с товарной стоимостью для части заказов.
- Вопрос 4: покупатель определяется customer_unique_id; повторный — человек с двумя и более разными order_id. Для соответствия базе вопроса учитываются все статусы. Отдельно показан вариант только delivered. Это доля повторных покупателей в наблюдаемом окне, не когортное удержание.
- Вопрос 5: группируем по исходному португальскому коду категории; английский перевод — подпись. Пустая категория выделяется отдельно; отсутствие перевода сохраняет исходную категорию.
- Просрочка: календарный день фактического вручения позже обещанного дня. Знаменатель — delivered-заказы с обеими датами. Время после полуночи в обещанный день само по себе не является просрочкой.
- В анализе доставки средняя оценка сначала считается по всем отзывам заказа, затем по заказам. Это явное правило EDA; оригинальные отзывы сохраняются. Наблюдаемая связь оценок с задержками не доказывает причинность.
- Запрещено восстанавливать отсутствующие события корзины, выкупа, возвратов или историю изменений справочников из одного снимка данных.

## Реализация core

- Статусное правило централизовано в core.dim_order_status.is_revenue; q01..q05.sql не фильтруют строковый статус самостоятельно.
- Покупатель в dim_customer — один человек. source_customer_id и исходный адрес относятся к fct_orders.
- Sentinel пустой категории в core: '__unknown__'. Английский перевод — nullable атрибут, исходная категория сохраняется.
- is_late — NULL без обеих дат; delivery_days использует elapsed days, estimate_days и delay_days — календарные дни.
- Разница общих сумм по is_revenue: SUM(order_amount) - SUM(payment_amount) = 2 001,88. Здесь SUM(payment_amount) пропускает неизвестный платёж, но соответствующий order_amount 143,46 участвует в общей стоимости. Это не замена NULL нулём в факте.
- Сумма известных индивидуальных разниц по заказам с обеими суммами: SUM(order_amount - payment_amount) = 1 858,42. Показатели имеют разные наборы сравнимых записей; оба сохраняются без исправления источника.
